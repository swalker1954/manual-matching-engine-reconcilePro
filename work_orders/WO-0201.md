## Background — what WO-0160 does (from manual walkthrough, local session)

Confirmed by manually working a GL Test File against a PowerBI export in
the local-testing session, before any code was written:

1. GL's `Action Number` column embeds a receipt number as free text,
   e.g. `Rct #: 05117614-1-FDJD5741PC`. The receipt key is the digit run
   after `Rct #: ` up to the first hyphen, with its single leading `0`
   stripped (`05117614` → `5117614`), giving a 7-digit key.
2. PowerBI's export carries the same value as a plain integer in a
   `ReceiptNumber` column (no leading zero, since it's numeric).
3. Match rule: look up the stripped key in PowerBI's `ReceiptNumber`. A
   receipt can appear as multiple PowerBI rows (allocation-code splits of
   one deposit) — when it does, search those rows for the one whose
   `Amount` **exactly** equals the GL row's `Net Amount`. If none match on
   amount, treat as unmatched and move on (do not guess).
4. On an exact amount match, take that PowerBI row's `BankID` value and
   write it onto the GL row.

**This exact algorithm, its precise output column name/shape, and which
local module implements it are all still pending WO-0160** — the above is
the confirmed *behavior*, not yet a confirmed *implementation contract*.
Do not start WO-0201 implementation from this description alone; get
WO-0160's actual diff first (see Prerequisites).

## Naming collision to resolve before implementation

`cloud_engine.py`'s existing data shape already has a `Bank_ID` field —
per the cloud session's own investigation, this is a **pre-existing, unrelated
row identifier that Data Prep has always produced**, not a bank
designation. WO-0160's new field must not silently collide with this
name. Confirm WO-0160's actual field name once known, and if it clashes,
use a distinguishable name on the cloud side (e.g. `PowerBI_Bank_ID` or
whatever the local implementation settles on) with a comment noting the
collision risk.

## Scope (tentative — firm up once Prerequisites are satisfied)

1. Add a second file-upload input to the cloud batch/upload flow for the
   PowerBI export, mirroring how the bank file is already accepted
   today (`cloud_batch.py`), scoped per-organization like every other
   batch input.
2. Call WO-0160's matching function from the cloud pipeline at the
   equivalent point the local pipeline calls it — reusing the
   unmodified `reconciliation_engine.*` function directly, per the
   pattern `cloud_engine.py` already follows for all seven existing
   engines ("Reuses the existing, unchanged reconciliation-engine
   business logic... No matching algorithm is modified in any way").
3. **No Postgres schema migration should be needed.** `cloud_batches`
   and `cloud_engine_result_rows` already store `data_source`/result
   rows as JSON (`data_source_json`, `row_json`), not normalized
   columns — the new field only needs to be included when that JSON is
   built, the same way every other derived column already flows
   through today.
4. Surface the new field in cloud Query / Matching Workbench display,
   coordinating with whatever the WO-0200-series UI session has already
   built for those screens (it owns the visual/UI layer; this work
   order only owns wiring the data through).

  to the cloud UI line's existing conventions (WO-0200 series).
